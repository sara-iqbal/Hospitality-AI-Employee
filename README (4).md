# Hospitality Enquiry AI Employee, a prototype

This project is a small working prototype of the customer journey Zube describes for hospitality operators: an enquiry comes in, gets answered, gets qualified, moves to a confirmed next action, and lands in a single customer record ready for a human to pick up when needed.

It was built to prepare for an interview, as a way of showing the mechanics of that idea rather than just describing it.

## The problem

Small hospitality operators (independent hotels, boutique groups, guesthouses) receive booking enquiries across many channels at once: phone, email, WhatsApp, live chat, and messages through booking sites. Handling all of that manually creates five recurring problems:

1. **Slow first response.** Enquiries that arrive outside working hours can sit unanswered for hours. Guests interested enough to message often book elsewhere before anyone replies.
2. **Inconsistent qualification.** Reading a free-text message and correctly capturing the room type, dates and party size takes attention that is easy to rush on a busy day, so quotes come back wrong or incomplete.
3. **No next action confirmed.** Even a well-qualified enquiry can quietly die if nobody locks in a concrete next step, such as a provisional hold, a quote, or a viewing.
4. **Fragmented customer records.** An enquiry from WhatsApp lives on someone's phone, an enquiry from email lives in an inbox, and nothing connects them if the same guest reaches out twice.
5. **No visibility for leadership.** Without a single, consistent record of what came in, nobody can see which channel is underperforming or how much revenue is quietly at risk.

## The data

I don't have access to a real hospitality operator's enquiry data, so I generated a synthetic dataset of 1,200 guest enquiries, modelled on how a small hotel group's inbound messages typically look: channel mix, free-text messages with realistic phrasing, room types, party sizes, requested dates, and a plausible booking value per enquiry.

For every enquiry, the dataset simulates two parallel outcomes:

- **Baseline**: how the enquiry would typically be handled today, with response times drawn from a long-tailed distribution (much slower out of hours), a qualification success rate around two thirds, and a next-action confirmation rate around 45 percent.
- **AI employee**: how the same enquiry would be handled by an always-on AI employee, with response times in the range Zube states on its own site (around 18 seconds), consistent qualification, and a next-action confirmation rate above 90 percent.

The generation logic lives in `generate_data.py`, and the same logic is walked through step by step, with explanations, inside the notebook.

## What I built

- **`Hospitality_AI_Employee_Prototype.ipynb`**: a Colab-ready notebook that generates the dataset, then works through each of the five problems above with real numbers and charts computed from the data. It includes a small rule-based intent-extraction function that reads a raw guest message and pulls out structured details (room type, party size, dates, extra questions like breakfast or parking), which stands in for the step an LLM call (for example, the Claude API) would handle in a production system. The rest of the pipeline (respond, qualify, arrange, log, handoff) does not need to change if that one step is swapped for a real model call.
- **`dashboard/index.html`**: a static dashboard summarising the same findings visually, meant to be opened directly or deployed with GitHub Pages. It does not require a server or build step. It reads its numbers from `dashboard/data.js`, which is generated by the same script as the dataset.
- **`data/hotel_enquiries.csv`**: the full synthetic dataset, 1,200 rows.
- **`generate_data.py`** and **`intent_extraction.py`**: the underlying generation and extraction logic, kept as plain, readable Python.

## What the numbers show

| Measure | Baseline | AI employee |
|---|---|---|
| Average time to first response | around 3 hours | around 18 seconds |
| Enquiries correctly qualified | around 67% | around 97% |
| Next action actually confirmed | around 45% | around 92% |
| Customer record reliably logged | around 51% | 100% |
| Estimated revenue at risk from lost enquiries | high | close to zero |

These figures come from the synthetic dataset described above, not from any real Zube customer. The point of the prototype is the mechanism it demonstrates, not the specific numbers: a consistent, always-on first response, a structured qualification step, a confirmed next action, a single customer record per enquiry, and a rollup that gives leadership visibility they do not currently have.

## How to run it

**Notebook**: open `Hospitality_AI_Employee_Prototype.ipynb` in Google Colab or Jupyter and run all cells. It has no dependencies beyond `pandas`, `numpy` and `matplotlib`, and needs no API key since the intent-extraction step is rule-based for portability.

**Dashboard**: open `dashboard/index.html` directly in a browser, or deploy the whole repository with GitHub Pages and visit `dashboard/index.html`. It loads chart data from `dashboard/data.js` in the same folder.

**Regenerating the data**: run `python3 generate_data.py` from the project root. This rewrites `data/hotel_enquiries.csv` and `dashboard/data.js` from the same random seed, so the numbers stay reproducible.

## Honest limitations

- The dataset is synthetic. It is built to be realistic, not to represent any real operator's actual enquiry volume or conversion rates.
- The intent-extraction step is a simple rule-based function, not a language model, so it works well on the structured phrasing in this dataset but would need a real LLM call to handle the far messier phrasing of genuine guest messages.
- The "AI employee" side of the simulation represents a target outcome based on the response-time figures Zube states publicly, not a live, tested system.

## Why hospitality specifically

Zube's own published customer stories include a leasing operator (The Stay Club) and a student housing operator (micampus Residencias), both of which describe the same underlying pattern this prototype models: enquiries lost to slow replies, and value in having a virtual agent available around the clock. Hospitality is one of Zube's four stated target segments alongside leasing, travel and vehicle rentals, and it is a natural fit for the same enquiry-to-booking pattern.
